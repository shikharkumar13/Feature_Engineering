    Over eight notebooks, this series built a toolkit: filling missing values, scaling skewed columns, encoding categories, creating new columns and selecting the useful ones. Every step came with the same warning, and until now the only thing enforcing it was memory. This notebook turns "fit only on training data" from a habit into something built into one object. Then it measures what relying on memory alone was actually risking.

    Start hereIntroduction#

    Notebook 3 stated the rule in full, and it has come back in every notebook since: anything with a fit method learns from data, and everything it learns must come from the training set. Followed correctly by hand, eight times, the rule works. But it depends on nobody ever forgetting it, in the ninth notebook or the ninetieth. Pipeline and ColumnTransformer take the rule out of your memory by making the wrong order of steps hard to write by accident.

    That's the honest reason to use them. The less honest reason, repeated so often it's become folklore, is that skipping a pipeline will wreck your score. Section 2 measures what these leaks are actually worth, for four of the six transformer types. The answer ranges from a millionth of an AUC point to a huge 0.27 of accuracy. The whole case for a pipeline is that you never know in advance which end of that range you're at.

    Section 1A pipeline is one object with one fit#

    The whole safety idea behind this notebook fits in one sentence. Here's exactly what that sentence rules out

    A Pipeline is a list of (name, step) pairs. Every step except the last must have both fit and transform. The last one only needs fit, which is why it's usually the model. Calling .fit() goes through the list once, calling fit_transform on each step and passing the result to the next. Calling .predict() goes through the same list calling only transform, and never calls fit again.

    That last point is the whole safety idea: there's no way for predict to refit anything.

    PythonThree numeric columns, one pipeline, one fit
    NUMERIC = ['tenure', 'MonthlyCharges', 'TotalCharges']

simple = Pipeline([
    ('impute', SimpleImputer(strategy='median')),
    ('scale',  StandardScaler()),
    ('model',  new_lr()),
])

simple.fit(X[NUMERIC], y)

print('steps:', list(simple.named_steps))
print()
print('what each fitted step learned, all of it from the rows passed to fit:')
print('  imputer medians:', simple.named_steps['impute'].statistics_.round(2))
print('  scaler means:   ', simple.named_steps['scale'].mean_.round(2))
print('  model coefs:    ', simple.named_steps['model'].coef_.round(3))
print()
print('5-fold AUC %.4f  (notebook 1 baseline: 0.8087)'
      % cross_val_score(simple, X[NUMERIC], y, cv=CV, scoring='roc_auc', n_jobs=1).mean())

    Section 2How much is each kind of leak actually worth#

    The leakage rule has come up for every type of transformer in this series. Here, four of the six are measured side by side, with the same model and the same seed

    NotebookTransformerWhat it learns
    2imputera median or mean
    3scalera mean and standard deviation
    4encodera list of categories, or a target average per category
    6vectorizera vocabulary
    7group aggregatea statistic per group
    8selectorwhich columns survive

    Every row in that table is a fit, and every one of them can be run on the whole dataset before splitting. The usual advice stops at "don't do that." This section measures it instead for the scaler, the imputer, the target encoder and the selector (the vectorizer and group-aggregate leaks were measured in notebooks 6 and 7). The sizes turn out to be very different, and that difference is the useful part.

    The recipe is the same for each row. The leaky version fits the transformer on all the data, then cross-validates the model on the result. The honest version puts the same transformer inside a pipeline, so each fold refits it on its own training rows. Same folds, same model, same seed every time.

    One part in a million. That's a real effect, but a tiny one: the slightly different means and standard deviations shift the regularized model's fit by a hair.

    The reason it's so small is right below. A mean over all 7,032 rows and a mean over one training fold's 5,625 rows differ by less than one percent on every column, because a mean is stable, and removing a random fifth of the rows barely moves it. So the leak tutorials use to scare people is, here at least, worth nothing.

    PythonTarget encoding, on the 322-category bundle column

    Output
    encoder  leaky 0.845031   honest 0.824909   difference +0.020121

  bundle categories: 322, median size 9 rows, 84 of them have 5 rows or fewer

    Two points of AUC. Notebook 4 measured this same encoder on this same column and got 0.8450 leaked against 0.8250 honest. The leaked figure matches exactly here, and the honest one is a ten-thousandth away. The reason is category size. The median bundle has only 9 rows, and 84 bundles have 5 or fewer. In a category that small, each row's own label is a big part of the category's average, so the encoder is handing the model a smoothed copy of the answer.

    Notebook 7 showed the leak shrinks roughly as 1 / group_size, which is why a 322-category column leaks and a 3-category column hardly does. TargetEncoder avoids this by cross-fitting internally. That's not something a pipeline gives you automatically. It's something this class does on purpose, and it's worth knowing the difference between the two kinds of protection.

    One caveat on the number: the leaky version uses a plain, unsmoothed category mean, while TargetEncoder also smooths small categories toward the overall rate. So the 0.020 measures the naive approach against the correct one, and a small part of it may come from smoothing rather than the leak alone.

    PythonSelection, twice: once harmless, once not

    Same transformer, same mistake, two very different answers. On 2,000 pure-noise columns with a coin-flip target, selecting first reports 74.5% accuracy for a problem whose true answer is 50%. On six real Telco columns, the same mistake costs nothing. The last two lines of output show why, and it's the most useful idea in this section: the less stable the selection, the bigger the leak.

    On the real columns, all five folds pick the same three, so choosing them in advance changes nothing. On the noise columns, one column survives every fold and 68 are picked by at least one. Each of those disagreements is the selector fitting itself to rows it's about to be tested on. Notebook 8 reached the same conclusion from the other direction, with the same two counts.

    That spread is the real argument, and it's different from the one usually given. If leaking a scaler cost two points of AUC, everyone would already be careful with scalers and nobody would need a pipeline to enforce it. Instead it costs a millionth of a point, so being careful with scalers feels like superstition. People then carry that carelessness over to encoders and selectors, which is exactly where it costs real money.

    A pipeline is worth it because you can't tell which row of that table you're in until you've already done the work properly. And it costs nothing to be right about all six at once.

    Notebook 6 made a sharper version of this point: you can't measure how much a leak is worth from inside the leaky experiment, because the number you'd use to decide is the contaminated one. The table above only exists because the honest version was calculated too.

    Section 3ColumnTransformer, and seeing what came out of it#

    A plain Pipeline applies every step to every column. That's fine when all columns are numbers, and useless as soon as they aren't

    You can't scale PaymentMethod, and you can't one-hot encode MonthlyCharges. ColumnTransformer takes a list of (name, transformer, columns) entries, runs each one on its own group of columns, and joins the results side by side. Any entry can itself be a small Pipeline, which is how one group of columns gets more than one step.

    PythonThe whole assembly, as one object
    def count_services(frame):
    """nb7's num_services: how many of the nine services this customer actually has."""
    return frame.isin(['Yes', 'DSL', 'Fiber optic']).sum(axis=1).to_frame('num_services')

def service_feature_names(transformer, input_features):
    return ['num_services']

service_counter = FunctionTransformer(count_services, feature_names_out=service_feature_names)

def make_preprocessor():
    return ColumnTransformer(
        transformers=[
            ('num', Pipeline([('impute', SimpleImputer(strategy='median')),
                              ('scale', StandardScaler())]), NUMERIC),
            ('svc', Pipeline([('count', service_counter),
                              ('scale', StandardScaler())]), SERVICES),
            ('ord', OrdinalEncoder(categories=CONTRACT_ORDER), ORDINAL),
            ('nom', OneHotEncoder(handle_unknown='ignore', drop='if_binary',
                                  sparse_output=False), NOMINAL),
            ('hi',  TargetEncoder(random_state=SEED), ['bundle']),
        ],
        remainder='drop',
        verbose_feature_names_out=False,
    )

def make_full_pipe():
    return Pipeline([('prep', make_preprocessor()), ('model', new_lr())])

    set_output(transform='pandas') may be the most useful line in this notebook for everyday debugging.     Section 4Custom transformers, stateless and stateful#

    Eventually you'll need a transformation scikit-learn doesn't have. The interface is small, and one question decides how to write it

    The interface is small: a fit that returns self, and a transform that returns the transformed data. BaseEstimator and TransformerMixin add get_params, set_params and fit_transform for free. But before writing a class, ask one question: does this transformation actually learn anything?

    num_services counts how many of nine columns say yes for a row. That count depends only on that one row: no training data, nothing stored, nothing that could leak. A transformation like that doesn't need a class, which is why it already appeared as FunctionTransformer(count_services, feature_names_out=service_feature_names).

    A stateless transformer is the one case where doing the work outside the pipeline is actually safe, since there's no fit step to run on the wrong rows. It still belongs in the pipeline, though, so the saved model knows how to build that column when serving, without anyone having to remember the formula.

    Now a transformer that does learn something. Notebook 4 found that one-hot encoding all 322 bundles scored 0.8007, worse than dropping the column, and that grouping rare categories together fixed it. But to group rare categories, you have to know which ones are rare, and that's a fact about the training rows, not about the column in general.

    PythonA custom grouper, fit two different ways
    class RareCategoryGrouper(BaseEstimator, TransformerMixin):
    """Keep categories seen at least `min_count` times in training, send the rest to 'Other'."""

    def __init__(self, min_count=20, other_label='Other'):
        self.min_count = min_count
        self.other_label = other_label

    def fit(self, X, y=None):
        counts = pd.DataFrame(X).iloc[:, 0].value_counts()
        self.frequent_ = set(counts[counts >= self.min_count].index)
        self.n_seen_ = len(counts)
        return self

    def transform(self, X):
        column = pd.DataFrame(X).iloc[:, 0]
        return column.where(column.isin(self.frequent_), self.other_label).to_frame('bundle_grouped')

    def get_feature_names_out(self, input_features=None):
        return np.array(['bundle_grouped'])


on_everything = RareCategoryGrouper(min_count=20).fit(X[['bundle']])
X_dev, X_hold, y_dev, y_hold = train_test_split(X, y, test_size=0.2, random_state=SEED, stratify=y)
on_train_only = RareCategoryGrouper(min_count=20).fit(X_dev[['bundle']])

print('fitted on all 7,032 rows: %d categories kept, plus Other' % len(on_everything.frequent_))
print('fitted on the 5,625 training rows: %d categories kept, plus Other' % len(on_train_only.frequent_))

    76 categories against 61. Fitting the grouper on everything doesn't just nudge a few numbers. It changes the width of the feature matrix, using rows the model will be tested on. This case deserves a close look, because people miss it most often. RareCategoryGrouper never touches y, so it can't leak the target, and in that narrow sense it's safe.

    But it can still make your list of features depend on the test rows, and that's what happened here: fifteen extra columns exist only because those rows were visible during fitting. Notebook 8 found the same issue with VarianceThreshold, which also ignores the target but still decides which columns exist. Part of this gap is simply that min_count=20 is an absolute count: with 25% more rows, more categories reach 20. A threshold given as a fraction of rows would move less, but it would still be learned from whatever rows it sees.

    The point to remember

    Not looking at the target isn't the same as not looking at the data. A transformer can follow the leakage rule as usually stated and still let your test set shape which columns your model sees.

    Section 7What you are allowed to claim#

    We now have a best cross-validated score of 0.8425, and it's tempting to write it down as the final answer. It isn't, for the same reason notebook 8 ended on

    A score used to choose between options is no longer an unbiased estimate. From here on there are three different numbers to keep apart.

    Quoting the winner inflated the score by just +0.0001, and the whole search was worth +0.0002. Both numbers tell us more than a big number would have. Notebook 8's rule explains the first one: the inflation from picking a winner grows with how much the candidates disagree. All 81 candidates here sit inside a narrow 0.0072 band, so there's almost nothing to overfit, and picking the best one is nearly free.

    In notebook 8's noise problem, where 2,000 candidate columns disagreed wildly, picking the "best" ones inflated accuracy by 0.27.

    The idea this notebook shares with notebook 8

    Selection optimism, leak size and candidate instability are closely linked: the more the options disagree, the more choosing among them inflates the score. That applies to choosing features, choosing hyperparameters and choosing between whole models.

    The second number is the one to take to work. Eighty-one fits bought two ten-thousandths of AUC, while deciding what the columns meant, back in notebooks 1, 4 and 7, was worth 0.0329. And even that +0.0002 shouldn't be taken seriously as a gain: the five outer folds range from 0.8358 to 0.8518, so a difference in the fourth decimal place is well inside the noise. The honest summary: the search bought nothing measurable, and the column decisions bought over three points of AUC.

    This is the failure most likely to catch you, and it usually happens at the end of a long training run instead of during development, when it would be cheap to fix. Pickle, which joblib uses, stores functions and classes by reference, not by value. A lambda has no importable name, so it can't be referenced, and it can't be saved.

    Libraries like cloudpickle can save lambdas, but loading still depends on having the same code available. That's why service_feature_names in section 3 is a named function instead of the lambda it wants to be.

    The same rule applies to RareCategoryGrouper. The saved file holds a pointer to the class, not the class itself, so whatever loads it needs the same class importable from the same place. A custom transformer defined in a notebook cell won't load anywhere else. Put custom transformers in a proper module and ship it with the model file.

    The scikit-learn version matters for a similar reason. The saved file does record which version wrote it, and loading it under a different version raises an InconsistentVersionWarning. But that's only a warning, nothing stops the load. The result can work perfectly, fail loudly or quietly behave differently. So pin your versions next to the model file, every time.

    Wrap-upKey things to remember from this notebook#

    A pipeline doesn't make your model better by itself. Building one here took the score from 0.8087 with three numeric columns to 0.8416 with everything handled properly, but each of those gains came from an earlier notebook, from thinking carefully about what a column means. The pipeline stops that work from being undone by accident.

    The leakage rule is worth very different amounts depending on what leaks. Fitting a scaler on all the data cost 0.000001 AUC here, and fitting an imputer cost 0.000134. Both are nothing, because they learn summary numbers that a fifth of the rows barely changes. Target encoding a 322-category column cost 0.020 AUC, and selecting 20 features from 2,000 noise columns inflated accuracy by 0.27. You never know in advance which case you're in, and a pipeline covers them all for free.

    Not looking at the target isn't the same as not looking at the data. RareCategoryGrouper never touches y, yet it kept 76 categories when fit on everything against 61 when fit on training rows only, changing the width of the feature matrix using rows it was about to be tested on.

    ColumnTransformer works best with explicit column lists, and remainder='drop' should stay the default. That one setting kept customerID out of the model and turns the transformer into a schema that fails loudly when the input changes shape.

    Turn on set_output(transform='pandas') while building. Debugging an unlabeled numpy array with eighteen columns wastes an afternoon. Remember it doesn't work with sparse one-hot output, which matters for wide category columns.

    Ask whether a transformer learns anything before writing a class for it. Stateless work like counting services fits in a FunctionTransformer. Stateful work needs a proper fit to store what it learned. Check whether scikit-learn already has it: the hand-written rare-category grouper scored 0.8416 against 0.8415 for OneHotEncoder(min_frequency=20), one argument instead of a class to maintain.

    A feature is worth what it adds to the features already there, not a fixed amount. bundle was worth 0.0163 in notebook 4 on a bare numeric baseline, and only 0.0017 here once Contract, PaymentMethod, InternetService and num_services were in the model. Three ways of encoding it finished within 0.0001 of each other.

    Preprocessing settings become hyperparameters inside a pipeline, and searching them barely mattered here. All 81 combinations spanned 0.0072. The biggest single factor was the model's own regularization strength, not preprocessing, and the whole search improved the honest estimate by 0.0002. Search tunes the last fraction of a percent. Deciding that Contract is ordinal was worth more than the entire grid.

    A score you used to choose something isn't a score you can quote. Here, quoting the best of 81 inflated the score by only 0.0001, because the 81 candidates agreed closely. In notebook 8, choosing the "best" of 2,000 noisy columns inflated accuracy by 0.27, because the candidates didn't agree at all. The more the options disagree, the more choosing among them inflates the result.

    Don't treat a single hold-out as the truth. Across eight random 20% splits, the gap between cross-validated and held-out AUC averaged +0.0002, with a standard deviation of 0.0113 and a range from −0.0146 to +0.0185. The gap we saw once was noise, not optimism, and it was bigger than every effect the grid search found.

    Save with joblib, and remember that pickle stores code by reference. Lambdas can't be saved with it. Custom classes must be importable from the same place wherever the model is loaded. The file records which scikit-learn version wrote it and warns on a mismatch, but doesn't stop the load, so pin your versions.

    In one sentence: a pipeline turns "remember to fit only on training data" from a habit you have to keep into a property of an object you can hand to someone else.

    Notebook 10 ends the series with the failures that survive all of this. A pipeline makes leakage through preprocessing structurally impossible. It does nothing about a column that should never have been collected, a feature that can't actually be computed at prediction time in production, or a model tuned so many times that the validation set stopped being a real test.
