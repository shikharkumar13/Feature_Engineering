    Feature Engineering · Notebook 7 companion articleFeature Construction and Domain-Driven Features

    Earlier notebooks built new columns along the way, like notebook 1's service count and notebook 6's style features. This notebook makes construction the main topic and asks which new column should exist. The danger is that a new feature can look like a discovery but just be a column you already had in a new form, or worse, a copy of the answer you're trying to predict. Both failures stay silent until you check.

    Start hereIntroduction#

    A model can only combine features in the ways its algorithm allows. A linear model adds them up with fixed weights. A tree splits on them one at a time. Neither will create "revenue per customer" or "number of services" by itself. A tree can only approximate them with many splits. If that quantity is what drives the outcome, the model wastes effort approximating something you could have just given it. That's the case for feature construction.

    It would be a short, happy notebook if building features couldn't go wrong. But it can, and in a way worse than wasted effort: a bad feature can look like a real discovery, pass a quick look at the code, and quietly rebuild a column you already had, or the answer itself.

    Section 1Two shapes of data#

    "Construction" means two different things, depending on how your table is laid out

    One row per entity. Telco has 7,032 rows and 7,032 customers. Everything about a customer is already on their row, so construction here means combining columns across the row: ratios, counts and flags.

    A transaction log. The e-commerce order file, covered in section 5, has 2,000 rows but only 200 customers, because each customer appears once per order. "How much has this person spent in total" isn't a column yet. Construction here means collapsing many rows into one summary per customer, which is a very different operation.

    Section 2Arithmetic combinations, and a check people skip#

    The obvious first step is to combine numeric columns. It skips a one-line check that can save you an afternoon

    Telco has three numbers to combine: tenure, MonthlyCharges and TotalCharges. The average lifetime bill is TotalCharges / tenure. Whether the current bill differs from that average sounds like a natural second feature.

    One subtlety: TotalCharges still has a use in a linear model. It's roughly the product of the other two, and section 3 shows that a linear model can't build a product by itself. So it adds a shape the model couldn't make, just not new facts.

    The habit to take away

    Before building ratios from a set of numeric columns, check whether one is already close to a product or sum of the others. It takes one correlation check and saves an afternoon of features that could never have worked.

    Section 3What the model can already do for itself#

    A second reason a new feature can add nothing: the model may already be able to build it

    A linear model calculates a weighted sum of its inputs. If you give it x1 + x2 as a new column, you've given it something it could already make from the coefficients it fits anyway. The same goes for any difference or weighted sum. Ratios and products are different: no linear coefficients can turn x1 and x2 into x1 / x2.

    Telco can't show this cleanly, since section 2 showed its columns are already redundant. California Housing, from notebook 3, has six columns that aren't built from each other, though some are related (AveRooms and AveBedrms rise together).

    PythonFour constructed columns: a sum, a difference, a ratio, and a product
    housing = fetch_california_housing(as_frame=True).frame
y_house = housing['MedHouseVal'].values

H_BASE = ['MedInc', 'HouseAge', 'AveRooms', 'AveBedrms', 'Population', 'AveOccup']
h = housing[H_BASE].copy()

h['rooms_plus_bedrooms'] = h['AveRooms'] + h['AveBedrms']     # linear combination
h['rooms_minus_bedrooms'] = h['AveRooms'] - h['AveBedrms']    # linear combination
h['rooms_per_bedroom'] = h['AveRooms'] / h['AveBedrms']       # not linear
h['occupancy_x_population'] = h['AveOccup'] * h['Population']  # not linear


def house_r2(cols, model='ridge'):
    if model == 'ridge':
        est = Pipeline([('scale', StandardScaler()), ('m', Ridge(alpha=1.0))])
    else:
        est = HistGradientBoostingRegressor(max_iter=150, random_state=42)
    return cross_val_score(est, h[cols], y_house, cv=KF5, scoring='r2', n_jobs=1).mean()

    So whether a new feature is worth building depends on the model. With a linear model, ratios are where the value is. With gradient boosting, expect small gains from rearranging columns, and spend most of your effort on features that bring in information the table doesn't already have. That's the next section.

    Section 4Construction that adds information#

    Section 2 failed because it rearranged three columns that only held two facts. The fix is to build from parts of the table the model hasn't seen

    PythonCounting subscribed services, and a ratio built from the count

    The gap between 0.7720 and 0.5239 is the size of the lie. A team shipping the first version would report a strong model, watch it fail completely in production, and not know why, because their hold-out agreed with their cross-validation all along.

    Now look at the training column, because it's the most useful part and the easiest to skip. The honest model has the highest training score, 0.8453, and the worst test score, 0.5239.     So this "honest" version is only half fixed. The test rows are clean, but each training row's rate still includes its own label, so the model learns to trust a feature that won't behave the same way on new rows. The full fix is cross-fitting, so no training row helps build its own value. That's what notebook 4's TargetEncoder does.

    That wide train-to-test gap is the model correctly signaling that the feature doesn't generalize. The leaky model shows 0.8061 in training against 0.7720 in testing, a gap of 0.03 that looks, by every usual check, like a healthy, well-regularized model.

    Why this gets past code review

    The more contaminated pipeline gave the more reassuring results. That's why leakage gets past reviews more easily than overfitting. Overfitting shows up as a wide gap between training and test scores. Leakage closes that gap, because the test rows are contaminated too, in the same direction. A small, healthy-looking gap isn't proof of an honest model. It's also exactly what a model that's wrong on both sides of the split looks like.

    Three rules come out of this, and they're really the same rule. Never aggregate the target over a group that includes the row being scored. Target statistics by group need cross-fitting, which is exactly what TargetEncoder did in notebook 4.

    Calculate group statistics from training rows only, then apply them to validation and test rows, with a clear plan for groups the training data never saw. And treat a big, unexplained jump as a reason to investigate, not celebrate: going from 0.5156 to 0.8089 by adding one column should make you suspicious.

    Section 8RFM, the oldest feature set that still works#

    Recency, Frequency, Monetary is decades older than machine learning, and its scoring step hides a real trap

    Direct mail marketers were using RFM long before machine learning, working it out by hand, because three numbers capture most of what matters about a customer: Recency, how long since their last order; Frequency, how many orders they've placed; and Monetary, how much they've spent in total. It's a good example because it's three simple aggregations plus one scoring rule, and the scoring rule is where the trap is.

    Plain qcut returns groups of 70, 50, 34 and 46. Those aren't quartiles. The cause is ties: qcut cuts on values, and every customer with exactly 8 orders has to go in the same bucket, so the edges land wherever the ties allow, not where an even split would put them.

    When ties are bad enough, qcut raises a duplicate-edge error. The common fix, duplicates='drop', hides the error but returns fewer bins than you asked for, still uneven. Ranking the values first, with method='first' to break ties by row order, gives exactly 50 in each group.

    That fix has a cost of its own. Two customers with exactly 8 orders can now land in different groups, decided only by which row came first. Equal-sized groups are bought with a slightly arbitrary split inside the ties. That's usually acceptable for RFM, but you should know it's happening. Notebook 3 hit the same issue with equal-frequency binning. Watch for it any time you bin a count.

    PythonScores and segments, built on the corrected ranking

    Section 9Aggregating over time without reading the future#

    Section 8's reference date was the day after the last order in the file. That's fine for a one-off segmentation, but wrong as soon as the result feeds a model that predicts anything

    Notebook 5 set the rule: a feature tied to a point in time can only use information available before that point. Group aggregates break this rule more easily than almost anything else, because a plain groupby().transform('sum') quietly includes every row in the group, even rows that happen after the row being scored.

orders_sorted['spend_to_date'] = grp.cumsum() - orders_sorted['line_total']
orders_sorted['orders_to_date'] = grp.cumcount()

    Section 10Automated feature construction#

    Everything in this notebook was built by hand. Tools can create the same combinations automatically, and knowing when that's worth it matters as much as knowing the techniques

    The best known is Featuretools, which uses a method called deep feature synthesis. You describe your tables and how they connect, and it applies aggregation functions (SUM, MEAN, COUNT, NUM_UNIQUE) and transform functions (DAY, MONTH, TIME_SINCE_PREVIOUS) across those connections, stacking them to a chosen depth. With this notebook's two tables, it would create SUM(orders.line_total), MEAN(orders.discount_pct), NUM_UNIQUE(orders.product_category) and hundreds more by itself. That's most of section 5 from a few lines of setup.

    It's worth using on large database schemas, where writing every aggregation by hand is a week of repetitive work, and in early exploration, to see which table relationships carry any signal before you invest effort. It also handles section 9's time-cutoff problem properly through a cutoff_time setting, which is more careful than most hand-written pipelines on the first try.

    It isn't always worth it. It creates hundreds or thousands of columns, most of them useless, so careful feature selection becomes a must, not an extra. It can't tell you that the churn curve it found is really a contract effect: it will happily create COUNT(services) and say nothing about what that count means, which was the whole point of section 4.

    And SUM(orders.is_returned) is exactly the kind of feature it will build without hesitation. So section 6's disaster can be automated too, at scale, unless you exclude target columns before running the tool.

    In practice, use both. Build the features your domain knowledge points to by hand, use automation to cover the combinations nobody has time to write, then select hard from everything it produces.

    Wrap-upKey things to remember from this notebook#

    Check whether columns depend on each other before building anything. Telco's TotalCharges is tenure × MonthlyCharges with an R-squared of 0.9991, so every ratio and product of those three columns just rebuilt one that already existed. None beat the 0.8087 baseline, and two scored 0.8086.

    A bucket table can show a pattern that isn't real. bill_ratio seemed to find a group with 39.7% churn, against about 21% to 27% for the other buckets. That bucket was 44.5% brand-new customers, against 12.1% overall. The feature was tenure in disguise and added nothing to a model that already had tenure.

    Sums and differences are easy to calculate and useless to a linear model. Adding AveRooms + AveBedrms moved Ridge's R-squared from 0.534771 to 0.534770. Ratios are different: AveRooms / AveBedrms added +0.018. AveOccup × Population cost 0.087, because multiplying amplifies skew, reaching 9.3 million against a median of 3,277. That's notebook 3's polynomial failure again.

    The model decides whether a new feature pays off, and by how much. The same ratio was worth +0.018 to Ridge and only +0.0015 to gradient boosting, which can roughly build a ratio itself by stacking splits. With trees, expect small gains from rearranging columns and spend your effort elsewhere.

    A new feature only helps if it adds information the model didn't have. Rearranging three redundant columns gained nothing. Counting nine unused service columns into num_services gained +0.0109. The question isn't "what can I calculate?" It's "what hasn't the model been told yet?"

    Check for a hidden cause before telling the story. The upside-down U of churn by num_services, peaking near 45% and falling to 5%, suggests a story about bundles and lock-in. It's mostly contract mix: 90% of three-service customers are month-to-month, against 3% of nine-service customers, and among month-to-month customers the curve flattens into a step. The feature still adds +0.0046 on top of Contract, so it stays, but charge_per_service adds nothing once Contract is in.

    Never aggregate the target over a group that includes the row being scored. On an is_returned column we proved can't be predicted, adding a group return rate took AUC from 0.5156 to 0.8089. The leaky version still scored 0.7720 on real hold-out rows, because the leak is inside the feature, not the split. Calculated from training rows only, the honest answer was 0.5239. Even that version still let each training row help build its own value. Group target statistics need cross-fitting, as TargetEncoder does.

    A row's own share of its group's average is about 1 / group_size, so the leak shrinks as groups grow. Grouping by customer (10 rows each) gave 0.7831, by product (40 rows) 0.6348 and by category (400 rows) 0.5414. The most detailed version of a feature like this is always the most tempting and the most contaminated.

    Leakage doesn't look like overfitting, which is why it gets past reviews. The leaky model scored 0.8061 in training and 0.7720 in testing, a gap that looks healthy. The honest model scored 0.8453 and 0.5239, and that wide gap correctly shows the feature doesn't generalize. Overfitting shows itself. Leakage hides by contaminating the test set too.

    Small groups give unreliable averages, in two ways. Customers with 3 to 5 orders had a return-rate spread of 0.1590, against 0.0710 for those with 13 or more, and simulation shows random variation explains that gap. The smallest band's higher mean is a separate question the data can't fully answer: p = 0.011 on just 70 orders could be real or chance. Smoothing toward the overall average, as in notebook 4, handles both cases.

    pd.qcut on tied whole numbers doesn't give you quartiles. Splitting 200 customers by order count gave groups of 70, 50, 34 and 46. duplicates='drop' hides the error without fixing the problem. Rank the values first with method='first'.

    groupby().transform() reads the whole group, including future rows. A customer's January order carried their full-year spend of 36,786.22. Use cumsum() - current_value for a strictly-prior total, and remember the first row of each group correctly has nothing before it.
