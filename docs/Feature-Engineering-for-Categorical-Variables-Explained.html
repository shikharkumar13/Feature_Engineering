    Feature Engineering · Notebook 4 companion articleFeature Engineering for Categorical Variables

    Models work with numbers. Categories are labels. Every technique in this notebook turns one into the other, and each one makes an assumption about the data that can be right or wrong. Coding contract length as 0, 1, 2 says two years is as far above one year as one year is above month-to-month. Make the same kind of claim about payment method, and the model learns something false without any warning.

    Dataset
    Telco Customer Churn, plus one engineered 322-category column
    Stack

    Start hereIntroduction#

    Notebook 3 showed that every numeric transformation makes an assumption, and that the wrong one can quietly wreck a model. Categories need the same care, because a model can't use them at all until you turn them into numbers.

    A lot of code treats encoding as a formatting step: strings go in, numbers come out, the errors stop. But every encoding choice makes a claim about how the categories relate to each other, and scikit-learn will build whatever claim you give it, true or not.

    If you say a two-year contract is twice as far from month-to-month as a one-year contract, and that's roughly true, the model gets useful information for free. Say something similar about payment methods, where no such distance exists, and the model doesn't push back. It just learns something false and uses it confidently.

    This notebook covers six approaches to the same problem, each with a measured cost and benefit:

    • label and ordinal encoding
    • one-hot encoding
    • target encoding
    • frequency encoding
    • the hashing trick
    • unseen and rare categories, which only cause trouble after a model ships

    None of these is always right or always wrong. Each one works best in specific situations, and this notebook shows what those are instead of giving you one default.

    The leakage rule from the last three notebooks comes back too, as notebook 3 promised. Encoders have a fit method like scalers and imputers. And in section 4 you'll meet the one encoder that learns from the target itself, where breaking the rule costs the most.

    The dataset, and one new column#

    Telco is a good fit because almost every column is a category. But none of its columns has many different values. One-hot encoding is the right answer for columns with just a few categories. The interesting trade-offs only show up when a column has too many categories to one-hot without thinking.

    So this notebook builds one. Each customer has some combination of nine services, and that combination describes their account in a way no single column does. Joining those nine columns into one string gives a real column with many categories. It stands in for the kind of many-valued column you meet in real work, like city, product or store.

    One honest note: you could also give the model the nine service columns directly. We use bundle because it's a real column with many categories, not because it's the only way to use this information.

    Section 1Reading a categorical column before encoding it#

    Two questions decide the right method. Answering them takes longer than writing the code

    Does the order mean anything? An ordinal column has a real ranking. Contract goes month-to-month, one year, two year, which shows rising commitment. A nominal column has no ranking. PaymentMethod has four values, and none is "higher" than another.

    Pandas can't answer this for you. Both kinds of column are just strings to the computer. Only a person who knows the subject can say which is which. That's why notebook 1 made Contract an ordered Categorical as soon as we knew the order, and promised this notebook would put that order to use.

    How many different values are there? With few categories, one-hot encoding is easy: a few new columns, plenty of rows behind each one. With many categories, it gets hard, and every alternative has a real trade-off.

    PythonEstablishing one baseline every encoding gets measured against
    cv = StratifiedKFold(n_splits=5, shuffle=True, random_state=RANDOM_STATE)

def logreg_auc(X):
    # Scaled logistic regression: sensitive to how categories are encoded
    return cross_val_score(make_pipeline(StandardScaler(), LogisticRegression(max_iter=3000)),
                           X, churned, cv=cv, scoring='roc_auc').mean()

def forest_auc(X):
    return cross_val_score(RandomForestClassifier(n_estimators=150, random_state=RANDOM_STATE, n_jobs=1),
                           X, churned, cv=cv, scoring='roc_auc').mean()

    Section 2Label and ordinal encoding#

    The simplest technique, and a default you should know about before it makes a choice for you

    The simplest way to turn a category into a number is to give each one an integer: Bank transfer becomes 0, Credit card becomes 1, and so on. When the column has a real order, this is the right approach, called ordinal encoding. When the column has no order, the same operation is usually called label encoding, and it quietly adds a ranking that doesn't exist.

    One default to know: if you don't give an order, scikit-learn sorts the categories alphabetically.

    Label encoding lowers the logistic regression's AUC by 0.0087, from one-hot's 0.8175 to 0.8088. The random forest barely changes, and even does very slightly better with one label column than with four one-hot columns. (The forest scores lower than logistic regression overall on these few columns. What matters here is how each model reacts to the change in encoding.) There's a clear reason for the difference between the two models.

    A linear model gives each column one coefficient. With payment method coded 0 to 3, it can only learn one effect that steadily rises or falls as the number goes up. The order is arbitrary, so there's no such steady effect, and the model is fitting a line through noise.

    A tree works differently. It splits again and again, so it can isolate the value 2 with two cuts and rebuild the original categories despite the meaningless numbers. That's why trees handle label encoding much better, and why people using gradient boosting often use it without much harm.

    Three results to look at.

    Correct ordinal encoding scores 0.8278 with one column. One-hot scores 0.8276 with three. They're basically tied, and the ordinal version uses a third of the columns, because the order we gave it was real information the model would otherwise have to work out itself. Notebook 1 also checked that the two steps are roughly even on the log-odds scale (about 1.8 and 1.5), which is why equal steps of 0, 1, 2 fit so well.

    The wrong order costs 0.0081 AUC. Same technique, same number of columns. The only change is which number went to which category. Ordinal encoding is only as good as the order you give it. A wrong order is worse than claiming no order at all (one-hot), though here it still beats leaving the column out.

    A small surprise: for Contract, alphabetical order (Month, One, Two) happens to be the right order, so the default would have worked by luck. Don't rely on that for any other column.

    One-hot didn't need to be told anything. It makes no claim about order, so it can't get the order wrong, and it found about the same pattern from the data. That safety is what the two extra columns buy you.

    What to take from this section

    Use ordinal encoding when you know the order, and write the order out yourself instead of trusting the default sort. Use one-hot when there's no order, or you're not sure. Never let alphabetical order set a ranking. OrdinalEncoder sorts alphabetically unless you pass the order, like OrdinalEncoder(categories=[['Month-to-month', 'One year', 'Two year']]). LabelEncoder always sorts, with no way to choose. Also, LabelEncoder is meant for the target, not for features. OrdinalEncoder is the one for features, since it takes two-dimensional input and works in a pipeline.

    Section 3One-hot encoding, and where it stops working#

    The standard choice for unordered columns, and a technique people keep using long after it stops helping

    One-hot encoding creates one 0/1 column per category. A customer on a two-year contract gets a 1 in contract_Two year and 0 in the other contract columns. There's no order implied, and each category gets its own coefficient. It's the right default for unordered columns.

    You'll sometimes see drop='first', which removes one column per feature. The dropped category becomes the "all zeros" case. That matters for a plain linear regression with no penalty, because a full set of one-hot columns always adds up to 1 and duplicates the intercept. Regularized models, which is scikit-learn's default for logistic regression, don't need it.

    But there's an easy-to-miss problem worth seeing first.

    The encoder only knows the categories it saw during fit. PaymentMethod has four categories in the full data. Fitting on these four sample rows, which only include three of them, gave three columns. Credit card (automatic) has no column at all, because the encoder never saw it.

    That's fine here, because it's a small demo sample. The lesson is that the list of categories is learned, and where it's learned from matters.

    This is also the main reason to use OneHotEncoder instead of the handier-looking pd.get_dummies. pd.get_dummies creates columns only for the categories in the data you give it. Train on data with four payment methods and you get four columns. Run the same line next month on data with only three, and you get three columns, with every column after the missing one shifted over by one place.

    The model then gets the wrong values in the wrong places, with no error.

    OneHotEncoder avoids this. It learns the full list of categories once, during fit, and always uses that same list, even for categories missing from the current data. That's why it belongs in a pipeline, like every other transformer in this series. get_dummies is fine for a quick look at the data. OneHotEncoder is what you use in anything that runs more than once.

    Now a problem that good code can't fix, because the code isn't the problem.

    One-hot encoding bundle makes the model worse than ignoring the column, dropping AUC from 0.8087 to 0.8007. Section 1 showed the column is useful, so the encoding is the problem, not the data. The picture below shows why.

    Three problems add up. Almost every column is mostly zeros. With 322 categories across 7,032 rows, the average column has a 1 in only about 22 rows. That's very little evidence to estimate a coefficient from. Rare categories get coefficients that are just noise. A bundle that appears twice gets its own column and coefficient, learned from two customers. The model's default penalty shrinks these coefficients a little, but not enough to stop them from fitting noise.

    325 columns for 7,032 rows gives the model more freedom than the data can support, so it fits patterns in the training folds that don't hold up in the validation fold.

    One more thing adds to the problem here: the pipeline scales every column. A 0/1 column that's 1 for only two customers has a tiny standard deviation, so after scaling, those two 1s become values around 59. Rare categories end up with extreme values. Many pipelines leave one-hot columns unscaled for this reason.

    This is where you need something other than one-hot. Sections 4 and 5 cover the alternatives, and section 6 shows that one-hot can still work if you deal with rare categories first.

    Section 4Target encoding, and the leak that comes with it#

    The strongest technique here for columns with many categories, and the one most likely to give you a great but false score

    Target encoding replaces each category with the average target value for that category. Each of the 322 bundles becomes the churn rate of its customers. So 322 categories become one number column with a clear meaning: a bundle encoded as 0.65 is one whose customers churn 65% of the time.

    It's the strongest technique in this notebook for columns with many categories. It's also the most likely to give you a great validation score for a model that fails in production. So we'll do it the wrong way first and measure the cost.

    PythonThe wrong way: building the mapping from the whole dataset, then cross-validating as if that were fine
    # THE WRONG WAY: compute the mapping from the whole dataset, then cross-validate
leaky_map = churned.groupby(telco['bundle']).mean()
leaky = numeric_only.assign(bundle_te=telco['bundle'].map(leaky_map))

print('Each bundle replaced by its churn rate, computed over all 7,032 rows:')
print(leaky[['bundle_te']].head(3).round(4).to_string(index=False))
print()
print(f'Cross-validated AUC: {logreg_auc(leaky):.4f}')
print(f'Baseline           : {BASELINE:.4f}')
print()
print('That looks like a large improvement. It is not real.')

That looks like a large improvement. It is not real.

    That looks like a big jump, from a baseline of 0.8087 to 0.8450. It isn't real, and it's easy to miss because nothing in the code looks broken.

    cross_val_score does split the data into five folds and holds one out each time. But the churn-rate mapping was built before the split, using every row, including the ones in the held-out fold. So when the model is tested on fold 3, each customer's encoded value was partly calculated from that customer's own churn result.

    It's worst where there's the least data. A bundle with only two customers gets the average of those two outcomes. If both churned, the value is 1.0, and the model sees that 1.0 for those same two customers during testing. This isn't a small bias. It's like giving the model part of the answer key.

    There are two separate problems, so there are two fixes. The first is the usual leakage rule from this series: fit the mapping inside a pipeline so it only sees training rows. The second is specific to target encoding and easy to miss: even within the training rows, a row shouldn't help build the value used to encode that same row. That needs internal cross-fitting instead of one pass. sklearn.preprocessing.TargetEncoder handles both for you.

    One quirk to know: the cross-fitting only happens in fit_transform. If you call fit and then transform on the same training rows, it's skipped and the second leak comes back. Inside a pipeline, this is handled for you.

    PythonThe right way: TargetEncoder, cross-fitted, sitting inside the pipeline
    # THE RIGHT WAY: TargetEncoder inside the pipeline, cross-fitted internally
preprocess = ColumnTransformer([
    ('numeric', 'passthrough', NUMERIC),
    ('target_encode', TargetEncoder(target_type='binary', random_state=RANDOM_STATE), ['bundle']),
])

proper = make_pipeline(preprocess, StandardScaler(), LogisticRegression(max_iter=3000))
proper_auc = cross_val_score(proper, telco[NUMERIC + ['bundle']], churned,
                             cv=cv, scoring='roc_auc').mean()

print(f'{"approach":38s} {"columns":>8s} {"AUC":>9s}')
print('-' * 58)
print(f'{"numeric only":38s} {3:>8d} {BASELINE:>9.4f}')
print(f'{"bundle one-hot":38s} {325:>8d} {logreg_auc(bundle_onehot):>9.4f}')
print(f'{"bundle target-encoded, LEAKED":38s} {4:>8d} {logreg_auc(leaky):>9.4f}')
print(f'{"bundle target-encoded, PROPER":38s} {4:>8d} {proper_auc:>9.4f}')

    The leak raised the score by 0.0200 AUC: a real 0.8250 reported as 0.8450. Think about what that means on a real project. You'd report 0.845 to your team, make decisions based on it, and then watch the live model perform like the 0.825 model it always was.

    The small size is what makes it dangerous. A leak that pushes a score to 0.99 gets caught, because nobody believes it. A leak that adds two points looks like a good day of feature engineering and gets through review.

    The real result is still very good. Proper target encoding reaches 0.8250 with one column, ahead of one-hot's 0.8007 with 322 columns and the 0.8087 baseline. That's a gain of 0.0163 from a single column. To make the leak concrete, the next cell shows it on a real held-out test set, not just in cross-validation.

    Smoothing, for categories with too little data#

    One problem is left even after fixing the leak. A bundle seen only three times, with no churners, has a rate of exactly 0.0. Taken literally, that tells the model these customers never leave. Three customers can't support a claim that strong.

    Smoothing fixes this by pulling each category's average toward the overall average, based on how much data the category has:

    encoded = (n × category_mean + m × overall_mean) / (n + m)

    Here n is the number of rows in the category, and m is a number you choose that controls how strongly the overall average pulls on small categories. Categories with lots of rows barely move. Categories with very few rows get pulled most of the way to the overall average.

    PythonSmoothing in practice, at three different strengths
    overall = churned.mean()
counts = telco['bundle'].value_counts()

examples = [counts.index[0], counts.index[1], counts[counts <= 3].index[0]]

print(f'Overall churn rate (the prior) = {overall:.3f}')
print()
print(f'{"customers":>10s} {"raw mean":>10s} {"m=0":>8s} {"m=10":>8s} {"m=50":>8s}')
print('-' * 48)
for bundle in examples:
    rows = telco['bundle'] == bundle
    n = rows.sum()
    raw = churned[rows].mean()
    smoothed = [(n * raw + m * overall) / (n + m) for m in (0, 10, 50)]
    print(f'{n:>10d} {raw:>10.3f} ' + ' '.join(f'{s:>8.3f}' for s in smoothed))
    Output
    Overall churn rate (the prior) = 0.266

 customers   raw mean      m=0     m=10     m=50
------------------------------------------------
      1180      0.087    0.087    0.089    0.095
       340      0.029    0.029    0.036    0.060
         3      0.000    0.000    0.204    0.251

    The bundle with 1,180 customers barely moves, from 0.087 to 0.095, even with the strongest smoothing. It has plenty of data. The bundle with 3 customers moves from 0.000 to 0.251, close to the overall rate of 0.266. With only three customers, the honest answer is "we don't know much about this group yet," and heavy smoothing says exactly that.

    TargetEncoder smooths automatically, using smooth='auto' by default, so we didn't have to do it by hand above. It's still worth understanding: if a target-encoded column's values all sit close to the overall average, smoothing on small categories is usually why. It's not a bug.

    When to use target encoding

    Use it on unordered columns with many categories, where one-hot would create too many columns and each category has enough rows for an average to mean something. Always use it inside a pipeline, cross-fitted and with smoothing on.

    Avoid it on small datasets, where most categories are rare and the encoding is mostly noise. Also avoid it on anything close to an ID column, where it basically lets the model memorize the target. Notebook 1's customerID would be the extreme example.

    Section 5Frequency encoding and the hashing trick#

    Two more options for columns with many categories. Neither uses the target, so neither can leak

    Frequency encoding replaces each category with how often it appears. It creates one column, doesn't use the target, and assumes that how common something is might help predict the outcome. One side effect: two categories with the same count get the same number, so the model can't tell them apart.

    PythonFrequency encoding, measured the same way as everything else
    frequencies = telco['bundle'].map(telco['bundle'].value_counts() / len(telco))
freq_encoded = numeric_only.assign(bundle_freq=frequencies)

print(f'Frequency encoded : AUC {logreg_auc(freq_encoded):.4f}')
print(f'Baseline          : AUC {BASELINE:.4f}')
print(f'Target encoded    : AUC {proper_auc:.4f}')
    Output
    Frequency encoded : AUC 0.8094
Baseline          : AUC 0.8087
Target encoded    : AUC 0.8250

    0.8094 against a 0.8087 baseline, which is basically nothing. It's important to report that plainly, because a null result is still a result. Frequency encoding helps when being rare actually means something, like in fraud detection, where an unusual merchant type is itself suspicious.

    Here, how common a service bundle is has almost nothing to do with churn, so the encoding captures something that doesn't matter much for this question. It's cheap and safe, so it's worth a quick try. But it's not a replacement for target encoding when you can use target encoding.

    The hashing trick works differently. It runs each category through a hash function and uses the result to pick a column. That way any number of categories fits into a fixed number of columns you choose ahead of time. Different categories will sometimes land in the same column, and the bet is that these collisions are rare and random enough not to matter much. (Scikit-learn's FeatureHasher also gives each category a random +1 or −1, so collisions tend to cancel out instead of piling up.)

    PythonHashing 322 categories into progressively fewer columns
    print(f'{"columns":>9s} {"categories per bucket":>24s} {"LogReg AUC":>12s}')
print('-' * 48)
for n_features in [8, 16, 32, 64]:
    hasher = FeatureHasher(n_features=n_features, input_type='string')
    hashed = pd.DataFrame(hasher.transform([[b] for b in telco['bundle']]).toarray(),
                          index=telco.index).add_prefix('hash_')
    score = logreg_auc(pd.concat([numeric_only, hashed], axis=1))
    print(f'{n_features:>9d} {telco["bundle"].nunique() / n_features:>24.1f} {score:>12.4f}')

print('-' * 48)
print(f'{325:>9d} {1.0:>24.1f} {logreg_auc(bundle_onehot):>12.4f}   <- one-hot, for comparison')
    Output
      columns    categories per bucket   LogReg AUC
------------------------------------------------
            8                     40.2       0.8087
       16                     20.1       0.8107
       32                     10.1       0.8142
       64                      5.0       0.8156
------------------------------------------------

    Hashing 322 categories into 64 columns scores 0.8156, beating one-hot's 0.8007 with a fifth of the columns. That's surprising, since hashing throws away information by letting categories collide.

    The reason is that one-hot's problem was never too little information. It was too many coefficients, each learned from too few rows. Hashing makes several categories share a column, so each column has many more rows behind it and the coefficients can be learned properly. The collisions cost less than the original sparseness did.

    Hashing is most useful at a scale where one-hot and target encoding struggle. With 500,000 different user IDs, one-hot isn't possible, and target encoding needs a 500,000-row lookup table stored with the model. A hasher doesn't store any list, since the hash function is fixed. It handles new categories without any special code, though a new category simply inherits whatever its column learned from others. Its memory use stays the same however many categories show up.

    The cost is that you can't interpret the columns. Column hash_37 is a random mix of unrelated categories and means nothing to a person, so you can't explain feature importance on hashed columns. Use hashing when the number of categories is truly huge, and use target encoding when it's just large.

    Section 6Unseen and rare categories#

    Two problems that only appear after deployment, and stay hidden while you work with one fixed dataset

    Unseen categories are values that show up at prediction time but never appeared in training. A new payment method launches, a new product is added, a new city gets a warehouse. The encoder has never seen that value but still has to handle it.

    Four different answers to the same question, and none is always right.

    • handle_unknown='error' fails loudly and right away. Use it when an unknown category means something broke upstream, and you want to know before making a prediction.
    • handle_unknown='ignore' sets all of that column's one-hot columns to zero. The model still predicts, using the other features. This is usually right for a service that must stay up. Keep in mind that "all zeros" is also a pattern the model never saw in training.
    • handle_unknown='infrequent_if_exist' puts an unknown value into the same bucket used for rare training categories. That's often better than all zeros, because that bucket was trained on real customers. The catch is that a brand-new category may not behave like the old rare ones.
    • TargetEncoder returns the overall mean, 0.2658, which is the dataset's churn rate. When you know nothing about a category, predicting the average is the right default.

    Rare categories are the related problem on the training side. They appear in training, but with so few rows that anything learned about them is noise. Section 3 showed one-hot encoding the full bundle column scored worse than dropping it, and rare categories were a big part of why.

    Wrap-upKey things to remember from this notebook#

    Encoding makes a claim about the data. It's not just formatting. Ordinal encoding claims an order, and that claim can be false. Contract in its true order scored 0.8278 with one column, matching one-hot's 0.8276 with three, while a shuffled order lost 0.0081. If you know the order, write it out, because OrdinalEncoder otherwise sorts alphabetically, and LabelEncoder always does.

    Label encoding hurts linear models but mostly doesn't hurt trees. On PaymentMethod it cost logistic regression 0.0087 AUC while the random forest was basically unaffected, because a linear model gets one coefficient per column and a tree can split it many times. Label encoding the 322-category bundle column scored 0.8087, exactly the baseline, wasting a column whose churn rates ran from 0% to 73.9%.

    One-hot stops working when there are too many categories. One-hot encoding all 322 bundles scored 0.8007, worse than dropping the column, because 325 columns across 7,032 rows leaves each coefficient learned from about 22 rows. Grouping everything under 20 rows into Other left 77 categories and raised the score to 0.8238.

    Target encoding is the strongest option here, and the easiest to leak with. Building the mapping before splitting reported 0.8450 against a real 0.8250. On a held-out test set, the leaked version claimed 0.8418 while the correct version delivered 0.8153. That gap is small enough to look believable, which is what makes it dangerous. Use TargetEncoder inside a pipeline so it's fitted on training rows only and cross-fitted within them. Calling fit then transform on training data skips the cross-fitting.

    Smooth target encodings toward the overall average. A bundle with 3 customers and no churners encodes as 0.000 raw and 0.251 smoothed, against an overall rate of 0.266. Three customers can't support a claim of zero.

    Hashing beat one-hot on this data, 0.8156 with 64 columns against 0.8007 with 322, because sharing columns gave each coefficient more rows to learn from. Use it when the number of categories is huge and storing a lookup table isn't practical, and accept that you won't be able to interpret the columns.

    Decide how to handle unseen categories before you deploy. handle_unknown='error' fails loudly, 'ignore' uses all zeros, and 'infrequent_if_exist' uses the rare-category bucket, which was trained on real data. Only 0 to 24 test rows were affected here, depending on the split, because this is one fixed dataset. In a live system, that number grows every month.
