Feature Engineering for Categorical Variables

Models do arithmetic. Categories are labels. Every technique in this notebook bridges that gap, and every single one of them makes a claim about the data that can turn out true or false. Turning a contract length into 0, 1, 2 asserts that two years sits above one year by the same distance one year sits above month-to-month. Make that same claim about a payment method and the model believes a lie, quietly, forever.

Dataset: Telco Customer Churn, plus one engineered 322-category column Stack: pandas · scikit-learn Companion to: Notebook 4

Encoding gets treated, in a lot of code, as a formatting step: strings go in, numbers come out, the model stops throwing errors, move on. That framing misses what's actually happening. Every encoding decision is a specific claim about the relationships inside a categorical column, and scikit-learn will faithfully build whichever claim you hand it, true or not. Assert that a two-year contract sits twice as far from month-to-month as a one-year contract does, and if that happens to match reality, the model gets a genuinely useful number for free. Assert the same kind of thing about which payment method someone uses, where no such distance exists, and the model doesn't reject the claim. It just learns something false and uses it with complete confidence.

This notebook works through six answers to the same underlying question, each with a real, measured cost and a real, measured benefit: label and ordinal encoding, one-hot encoding, target encoding, frequency encoding, the hashing trick, and the specific production failures, unseen and rare categories, that only show up after a model ships. The throughline across all six is that none of them is simply correct or simply wrong. Each one wins under conditions that can be stated precisely, and this notebook spends its effort finding those conditions rather than handing over a single default to reach for every time.

The dataset, and one engineered column

Telco suits this notebook well for a simple reason: almost every column in it is categorical. What it doesn't have on its own is a column with enough distinct categories to make the harder techniques necessary, since one-hot encoding is the right answer for anything with a handful of categories, and the interesting trade-offs only appear once a column has more categories than anyone would want to one-hot without thinking twice.

So this notebook builds one. Each customer subscribes to some specific combination of nine separate services, and that combination describes their account in a way no single existing column does. Joining those nine columns into one string produces a real high-cardinality feature, and it's the kind of column you'd actually construct on a real team, not a synthetic one invented purely to make a demonstration work.

1Reading a categorical column before encoding it

Two questions decide the right method, and answering them honestly takes longer than writing the encoding line itself

Does the order mean anything? An ordinal column carries a genuine ranking. Contract runs month-to-month, one year, two year, and that sequence describes steadily increasing commitment. A nominal column carries no such ranking. PaymentMethod has four values, and no defensible argument puts any one of them above another.

Pandas cannot answer this question for you, no matter how the data is stored. Both kinds of column arrive as plain strings and look byte-for-byte identical to the computer. The distinction lives entirely in domain knowledge that has to come from a person, which is why notebook 1 declared Contract an ordered Categorical the moment that knowledge was available, rather than leaving it as a plain string for pandas to guess at.

How many distinct values are there? Low cardinality makes one-hot encoding comfortable, in every sense that matters: few new columns, plenty of rows behind each one, nothing to think hard about. High cardinality makes it uncomfortable, and every alternative to it involves a real trade-off rather than a free upgrade.

2Label and ordinal encoding

The simplest possible technique, and a default behavior worth knowing about before it decides something for you

The simplest approach to turning a category into a number assigns each one a plain integer: Bank transfer becomes 0, Credit card becomes 1, and so on. When the column is genuinely ordered, this is exactly the right technique, and it has a name for that case: ordinal encoding. When the column carries no order at all, the identical mechanical operation is usually called label encoding, and it quietly inserts a ranking that was never there to begin with.

One default is worth knowing before it makes a decision on your behalf: when you don't specify an order yourself, scikit-learn sorts the categories alphabetically.

The order scikit-learn assigns when nobody tells it otherwise

Label encoding costs the logistic regression 0.0087 AUC, falling from one-hot's 0.8175 down to 0.8088. The random forest, by contrast, is barely touched, and if anything does marginally better with the single label column than with four separate one-hot columns. That split between the two model families isn't a coincidence, and it's worth understanding the mechanism rather than just the direction.

A linear model multiplies an encoded column by exactly one coefficient. Handed payment method encoded 0 through 3, it can only ever learn a single effect that rises or falls steadily as that number increases. Since the underlying ordering is arbitrary, no such steady effect genuinely exists in the data, and the model is left fitting a straight line through what amounts to noise. A tree, on the other hand, splits repeatedly: it can isolate the value 2 on its own with two well-placed cuts, and effectively reconstruct the original categories despite the meaningless numbering. Trees tolerate label encoding far better than linear models do, which is exactly why practitioners using gradient boosting often use it without much visible harm.

Three results, each worth pulling apart on its own.

Correct ordinal encoding reaches 0.8278 from a single column. One-hot reaches 0.8276 using three. The two are essentially tied, and the ordinal version gets there with a third of the columns, because the order supplied to it was real information the model would otherwise have had to reconstruct on its own from the raw categories.

The wrong ordering costs 0.0081 AUC. Same technique, same column count, and the only thing that changed between this run and the correct one is which integer got assigned to which category. Ordinal encoding is only ever as good as the order you supply, and supplying a wrong one is worse than making no ordering claim at all.

One-hot never had to be told anything. It makes no ordering claim whatsoever, so it cannot make a wrong one, and it recovered essentially the same pattern directly from the data. That safety is precisely what two extra columns buy you.

Practical guidance from this section

Use ordinal encoding when you genuinely know the order, and write that order out explicitly rather than trusting the default sort. Use one-hot when there's no order, or when you're not sure there is one. Never let alphabetical sorting decide a ranking for you, which is exactly what OrdinalEncoder and LabelEncoder do the moment you leave the order unspecified. And note that LabelEncoder is documented for encoding the target variable, not feature columns; OrdinalEncoder is the one built for features, since it accepts two-dimensional input and fits cleanly into a pipeline.

3One-hot encoding, and where it stops working

The default for nominal columns, for good reason, and also the technique people keep reaching for well past the point it stops helping

One-hot encoding creates a single binary column per category. A customer on a two-year contract gets a 1 in contract_Two year and a 0 in every other contract column. No ordering is implied anywhere in that scheme, and every category earns its own independent coefficient. It's the correct default for nominal columns, and there's a specific, easy-to-miss failure mode worth seeing directly before trusting it on a new column.

This is worth sitting with, because it's the entire argument for reaching for OneHotEncoder over the more convenient-looking pd.get_dummies. PaymentMethod has four real categories across the full dataset. Fitting on just these four sample rows, which happen to contain only three of them, produced exactly three columns. Credit card (automatic) gets no column at all, not because anything went wrong, but because the encoder fitting on this sample never once laid eyes on it.

That's harmless here, since this was deliberately fit on a small sample for demonstration. It becomes a genuine production outage when the identical thing happens between a training run and a batch of live traffic. pd.get_dummies looks at whatever data it's handed and creates columns for exactly the categories present in that data. Train on a file containing four payment methods and you get four columns; run the identical line next month on a batch that happens to contain only three, and you get three columns, quite possibly in a different order, and the model silently receives the wrong values sitting in the wrong positions with no error raised anywhere. OneHotEncoder avoids this by construction: it learns the full category list exactly once, during fit, and applies that same fixed list forever afterward, including columns for categories that happen to be entirely absent from whatever it's currently transforming. It belongs inside a pipeline for precisely the same reason every other transformer in this series does. get_dummies is fine for a quick, one-off look at the data; OneHotEncoder is what belongs in anything that will run more than once.

One-hot encoding bundle makes the model measurably worse than ignoring the column outright, dropping AUC from 0.8087 down to 0.8007. Section 1 already established the column is informative, so this is a failure of the encoding rather than a failure of the underlying data, and it's worth seeing exactly why in a picture rather than only in a single dropped number.

Three separate problems compound at once here. Each column ends up almost entirely zeros. With 322 categories spread across 7,032 rows, the average column reads 1 for only about 22 of them, which is very little evidence for a single coefficient to be estimated from. Rare categories produce coefficients that are pure noise. A bundle appearing exactly twice gets its own column and its own fitted parameter, estimated from two observations, and the model uses that parameter with exactly as much confidence as one estimated from a thousand. 325 columns against 7,032 rows hands the model far more freedom than the data can actually support, so it ends up fitting patterns specific to the training folds that simply don't carry over to the validation fold.

This is precisely the point at which something other than one-hot becomes necessary rather than merely nice to have. Sections 4 and 5 work through the alternatives, and section 6 comes back to show that one-hot itself can be rescued, provided the rare categories get dealt with first.

4Target encoding, and the leak that comes with it

The strongest technique in this notebook for high-cardinality columns, and the one most likely to hand you a beautiful, false validation score

Target encoding replaces each category with the average target value observed for that category. Every one of the 322 bundles becomes the churn rate of the customers who share it, and 322 categories collapse into a single numeric column that's directly, immediately meaningful: a bundle encoded as 0.65 is a bundle whose customers churn at 65%. It's the strongest technique this notebook covers for high-cardinality columns. It's also the one most capable of silently handing you an excellent validation score attached to a model that fails once it reaches production, so the honest way to introduce it is to do it wrong first and measure exactly what that costs.

The wrong way: building the mapping from the whole dataset, then cross-validating as if that were fine

That looks like a large improvement. It is not real.

That reads like a substantial improvement, from a baseline of 0.8087 up to 0.8450. It's not a real one, and the reason it survives casual code review is that nothing about the code looks obviously broken.

cross_val_score does split the data into five folds and truly holds one out on each pass. But the churn-rate mapping itself was built before that split ever happened, using every single row, including the ones about to sit in whichever fold gets held out. When the model is scored on fold 3, the encoded value it reads for each customer in that fold was computed partly from that exact customer's own churn outcome. The effect is worst precisely where the data is thinnest: a bundle appearing exactly twice takes the plain average of those two customers' outcomes, so if both of them churned, the encoded value is a flat 1.0, and the model reads that value back for those same two customers at the moment it's supposedly being evaluated on unseen data. That isn't a subtle statistical bias. It's the model being handed the answer key for part of its own exam.

Two separate fixes are needed here, because two separate things have gone wrong. The first is the leakage rule already familiar from every notebook in this series: fit the mapping inside a pipeline, so it only ever sees training rows. The second is specific to target encoding and easy to miss even once the first fix is in place: even within the training set, a single row shouldn't be allowed to contribute to the very mapping later used to encode that same row, which requires an internal cross-fitting scheme rather than a single pass over the training data. sklearn.preprocessing.TargetEncoder handles both automatically.

The right way: TargetEncoder, cross-fitted, sitting inside the pipeline
# THE RIGHT WAY: TargetEncoder inside the pipeline, cross-fitted internally
preprocess = ColumnTransformer([
    ('numeric', 'passthrough', NUMERIC),
    ('target_encode', TargetEncoder(target_type='binary', random_state=RANDOM_STATE), ['bundle']),
])

proper = make_pipeline(preprocess, StandardScaler(), LogisticRegression(max_iter=3000))
proper_auc = cross_val_score(proper, telco[NUMERIC + ['bundle']], churned,
                             cv=cv, scoring='roc_auc').mean()

print(f'{"approach":38s} {"columns":>8s} {"AUC":>9s}')
print('-' * 58)
print(f'{"numeric only":38s} {3:>8d} {BASELINE:>9.4f}')
print(f'{"bundle one-hot":38s} {325:>8d} {logreg_auc(bundle_onehot):>9.4f}')
print(f'{"bundle target-encoded, LEAKED":38s} {4:>8d} {logreg_auc(leaky):>9.4f}')
print(f'{"bundle target-encoded, PROPER":38s} {4:>8d} {proper_auc:>9.4f}')

The leak inflated the reported score by 0.0200 AUC: a true 0.8250 reported as 0.8450. It's worth sitting with what that gap actually means in a real project rather than treating it as an abstract statistic. You would have reported 0.845 to a team, made a rollout decision that assumed that number, and then watched the deployed model quietly perform like the 0.825 model it always actually was. The size of that gap is exactly what makes it dangerous: a leak inflating a score to 0.99 gets noticed immediately, because nobody believes it. A leak inflating a score by two points sails through review, because it looks like a good day of feature engineering rather than a bug.

The honest result underneath the leak is still excellent in its own right. Proper target encoding reaches 0.8250 using a single column, ahead of one-hot's 0.8007 from 322 columns, and ahead of the 0.8087 baseline that ignores the column outright. That's the largest single-column gain anywhere in this series so far. To make the leak concrete rather than purely statistical, it's worth watching it happen once on an actual held-out test set rather than only inside cross-validation.

The same leak, demonstrated on a genuine train/test split
train, test, y_train, y_test = train_test_split(
    telco, churned, test_size=0.25, random_state=RANDOM_STATE, stratify=churned)

# Version A: mapping built from ALL rows, including the test set
map_all = churned.groupby(telco['bundle']).mean()

    test[NUMERIC].assign(te=test['bundle'].map(map_train).fillna(prior)))[:, 1])

0.8418 against 0.8153. The first of those numbers is not a better model. It's the identical model being graded on an exam it had already secretly seen the answers to.

Smoothing, for categories with too little evidence to trust on their own

One issue remains even once the leakage itself is fully handled. A bundle seen exactly three times, none of whom churned, has an observed rate of a flat 0.0, and taking that number at face value tells the model those specific customers never leave, ever. Three observations cannot actually support a claim that strong.

Smoothing addresses this by blending each category's own average toward the overall average, weighted by how much evidence that category actually has behind it:

encoded = (n × category_mean + m × overall_mean) / (n + m)

Here n is how many rows the category has, and m is a chosen constant controlling how strongly the overall average pulls on categories with little evidence. Categories with plenty of rows barely move at all. Categories with almost no rows get pulled most of the way toward the prior.

Smoothing in practice, at three different strengths
overall = churned.mean()
counts = telco['bundle'].value_counts()

examples = [counts.index[0], counts.index[1], counts[counts <= 3].index[0]]

print(f'Overall churn rate (the prior) = {overall:.3f}')
print()
print(f'{"customers":>10s} {"raw mean":>10s} {"m=0":>8s} {"m=10":>8s} {"m=50":>8s}')
print('-' * 48)
for bundle in examples:
    rows = telco['bundle'] == bundle
    n = rows.sum()
    raw = churned[rows].mean()
    smoothed = [(n * raw + m * overall) / (n + m) for m in (0, 10, 50)]
    print(f'{n:>10d} {raw:>10.3f} ' + ' '.join(f'{s:>8.3f}' for s in smoothed))
Output
Overall churn rate (the prior) = 0.266

 customers   raw mean      m=0     m=10     m=50
------------------------------------------------
      1180      0.087    0.087    0.089    0.095
       340      0.029    0.029    0.036    0.060
         3      0.000    0.000    0.204    0.251

The bundle with 1,180 customers barely moves, from 0.087 to 0.095 even at the strongest smoothing tested. It has more than enough evidence to speak entirely for itself. The bundle with only 3 customers moves from a raw 0.000 all the way to 0.251, landing close to the 0.266 dataset-wide prior. With three observations, the honest thing to encode is close to "nothing specific is known about this group yet," which is exactly what heavy smoothing expresses numerically.

TargetEncoder applies smoothing automatically, controlled by smooth='auto' by default, which is why none of this had to be handled by hand in the pipeline above. Knowing the underlying mechanism still matters in practice: when a target-encoded column's values all sit suspiciously close to the overall mean, smoothing pulling on thin categories is usually the reason, not a bug.

When to reach for target encoding, and when not to

Reach for it on high-cardinality nominal columns, where one-hot would produce far too many columns, and where enough rows sit behind each category for an average to actually mean something. Always inside a pipeline, always cross-fitted, always with smoothing switched on. Avoid it on small datasets, where nearly every category ends up rare and the encoding becomes mostly noise, and avoid it on anything close to an identifier, where target encoding becomes close to a direct route to memorizing the target outright. Notebook 1's customerID would be the extreme version of exactly that failure.

5Frequency encoding and the hashing trick

Two more options for high-cardinality columns, and both ignore the target entirely, which means neither one can leak

Frequency encoding replaces each category with how often it appears in the data. It produces a single column, needs no access to the target at all, and carries one specific implicit claim: that how common something is might itself be predictive, independent of anything else about it.

Frequency encoding, measured the same way as everything else
frequencies = telco['bundle'].map(telco['bundle'].value_counts() / len(telco))
freq_encoded = numeric_only.assign(bundle_freq=frequencies)

print(f'Frequency encoded : AUC {logreg_auc(freq_encoded):.4f}')
print(f'Baseline          : AUC {BASELINE:.4f}')
print(f'Target encoded    : AUC {proper_auc:.4f}')
Output
Frequency encoded : AUC 0.8094
Baseline          : AUC 0.8087
Target encoded    : AUC 0.8250

0.8094 against a 0.8087 baseline. Essentially nothing, and reporting that plainly matters more than it might seem, since a negative or null result is still a result worth having on record rather than quietly dropping. Frequency encoding earns its keep specifically when rarity itself carries signal, which is genuinely true in domains like fraud detection, where an unusual merchant category is itself grounds for suspicion. Here, how common a particular service bundle happens to be has almost no relationship to whether that customer eventually churns, so the encoding faithfully captures a variable that simply doesn't matter much to this particular question. The technique is cheap, safe, and always worth trying quickly. It is not a substitute for target encoding when target encoding is actually available to you.

The hashing trick takes a different route entirely. It runs each category through a hash function and uses the result to select a column, mapping any number of categories, however many there are, into a fixed number of columns chosen in advance. Different categories can and will collide into the same column, and the working bet is that those collisions are rare and random enough not to matter much in practice.

Hashing 322 categories into progressively fewer columns
print(f'{"columns":>9s} {"categories per bucket":>24s} {"LogReg AUC":>12s}')
print('-' * 48)
for n_features in [8, 16, 32, 64]:
    hasher = FeatureHasher(n_features=n_features, input_type='string')
    hashed = pd.DataFrame(hasher.transform([[b] for b in telco['bundle']]).toarray(),
                          index=telco.index).add_prefix('hash_')
    score = logreg_auc(pd.concat([numeric_only, hashed], axis=1))
    print(f'{n_features:>9d} {telco["bundle"].nunique() / n_features:>24.1f} {score:>12.4f}')

print('-' * 48)
print(f'{325:>9d} {1.0:>24.1f} {logreg_auc(bundle_onehot):>12.4f}   <- one-hot, for comparison')
Output
  columns    categories per bucket   LogReg AUC
------------------------------------------------
        8                     40.2       0.8087
       16                     20.1       0.8107
       32                     10.1       0.8142
       64                      5.0       0.8156
------------------------------------------------
      325                      1.0       0.8007   <- one-hot, for comparison

Hashing 322 categories down into 64 columns scores 0.8156, beating one-hot's 0.8007 while using a fifth of the columns. That's genuinely surprising at first glance, since hashing deliberately throws away information by allowing categories to collide with each other. The explanation is that one-hot's problem was never a shortage of information; it was too many parameters being estimated from too few rows apiece. Hashing forces multiple categories to share a column, each resulting column ends up with far more non-zero rows behind it, and the coefficients that emerge become genuinely estimable rather than fitted from a handful of examples. The collisions cost noticeably less than the original sparsity did.

Where hashing earns its place is at a scale one-hot and target encoding both struggle with. With 500,000 distinct user IDs, one-hot is simply not feasible, and target encoding needs a 500,000-entry lookup table shipped and maintained alongside the model. A hasher needs no stored vocabulary of any kind, since the hash function itself is fixed in advance, so it handles categories it has genuinely never encountered without any special-case logic, and it runs in constant memory regardless of how many distinct categories eventually show up.

The cost is interpretability, and it's a real one. Column hash_37 holds an arbitrary mixture of unrelated categories and means nothing at all to a human reading it, so feature importance computed on hashed columns can't be explained to anyone afterward. Reach for hashing when cardinality is truly enormous, and prefer target encoding whenever cardinality is merely large rather than extreme.

6Unseen and rare categories

The two failure modes that show up only after deployment, and stay completely invisible while you're working with one fixed dataset

Unseen categories are values that appear at prediction time and were never present anywhere in the training data. A new payment method launches, a new product line gets added, a new city gets its own warehouse. Whatever encoder is sitting in the pipeline has never encountered that value and has to do something with it regardless.

How many unseen bundles show up, purely as a function of which random split gets drawn

Four different answers to an identical question, and none of them is automatically the right one to reach for.

  • handle_unknown='error' fails loudly and immediately. The right choice when an unknown category really does signal that something has gone wrong upstream, and you'd rather know about it before serving a prediction than after.
  • handle_unknown='ignore' encodes the row as all zeros across every one of that column's dummy columns. The model still returns a prediction, built entirely from whatever other features are available. This is usually the right behavior for a service that has to stay up regardless, and it's worth remembering that "all zeros" is itself a pattern the model never actually saw during training either.
  • handle_unknown='infrequent_if_exist' routes an unknown value into the same bucket already used for rare training categories, which is more principled than falling back to all-zeros, because that particular bucket has genuinely been trained on real data.
  • TargetEncoder returns the overall mean, 0.2658, which is exactly the dataset's churn rate. Knowing nothing specific about a category, predicting the dataset average is the correct default, not a fallback to apologize for.

Rare categories are the closely related problem on the training side. They're present during training, but with so few supporting rows that anything learned specifically about them amounts to noise. Section 3 already showed one-hot encoding the full bundle column scoring worse than dropping it outright, and rare categories were a large part of exactly why.

Reading that table from the bottom up tells the more useful story. Those two are close enough that the choice between them stops being about the score and becomes a question of engineering trade-offs instead. Target encoding is far more compact and needs careful cross-fitting to stay safe. Grouped one-hot is more transparent, structurally cannot leak the way target encoding can, and every one of its columns still means something a person can point to directly. On a production system, I would personally want a specific, strong reason before choosing the technique that fails silently over the one that simply cannot.

At the bottom of the table, label encoding and unrestricted one-hot both land at or below the baseline that ignores the column outright. Both took a genuinely informative column and rendered it useless, arriving at that failure from opposite directions: one destroyed every distinction the column carried, the other kept all 322 of them and handed the model nothing solid enough to actually estimate from.

Key things to remember from this notebook

Encoding is a claim about the data, not a formatting step. Ordinal encoding asserts an ordering, and that assertion can simply be false. Contract encoded in its true order scored 0.8278 from a single column, matching one-hot's 0.8276 from three, while the identical technique with a shuffled order lost 0.0081. If you know the order, state it explicitly, because OrdinalEncoder and LabelEncoder otherwise sort alphabetically and let spelling decide the ranking for you.

Label encoding hurts linear models and mostly spares trees. On PaymentMethod it cost logistic regression 0.0087 AUC while the random forest was essentially unaffected, because a linear model gets exactly one coefficient for the whole column while a tree can split it apart repeatedly. Label encoding the 322-category bundle column scored 0.8087, precisely the baseline, destroying a column whose churn rates genuinely ran from 0% to 73.9%.

One-hot stops working as cardinality grows. All 322 bundles one-hot encoded scored 0.8007, worse than dropping the column entirely, because 325 columns spread across 7,032 rows leaves each coefficient estimated from roughly 22 non-zero rows. Grouping everything under 20 rows into Other cut that down to 77 categories and lifted the score to 0.8238.

Target encoding is the strongest option here, and the easiest to leak with. Building the mapping before splitting reported 0.8450 against a true 0.8250, and on a genuine held-out test set the leaked version claimed 0.8418 where the honest version actually delivered 0.8153. That gap is small enough to look entirely plausible, which is exactly what makes it dangerous. Use TargetEncoder inside a pipeline, so the mapping is both fitted on training rows only and cross-fitted within them.

Smooth target encodings toward the prior. A bundle with 3 customers and zero churners encodes as a raw 0.000, and a smoothed 0.251, against a 0.266 overall rate. Three observations cannot honestly support a claim of zero.

Hashing beat one-hot on this data, 0.8156 from 64 columns against 0.8007 from 322, because forcing categories to share columns gave each coefficient far more supporting rows to learn from. Reach for it when cardinality is truly enormous and shipping a lookup table isn't practical, and accept that the resulting columns become uninterpretable.

Decide what happens to unseen categories before deployment, not after. handle_unknown='error' fails loudly, 'ignore' encodes all zeros, and 'infrequent_if_exist' routes into the rare bucket that was actually trained on real data. Only 4 test rows were affected here, because this is one fixed historical extract; in a live system, that number grows every single month.
